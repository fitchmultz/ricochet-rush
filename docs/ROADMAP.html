Roadmap

This is the canonical product roadmap for the project. The public goal is an original browser arcade game inspired by the brick-breaker genre, with adaptive board design powered by the Cursor SDK through a local server route.

Product name: Ricochet Rush.

Product Goals

  • Make a game that is fun on its own, not just a technology demo.
  • Build an original identity with a simple, game-first name.
  • Make the Cursor SDK useful to gameplay: board generation, adaptation, curation, and playtest loops.
  • Keep all SDK access server-side. Browser code must not assume secrets or direct SDK auth.
  • Keep the game easy to run and verify with npm run ci.

Public Positioning

Use this positioning in public docs:

An original 3D browser brick-breaker where an AI board designer creates, validates, and evolves playable arcade layouts.

Public docs should keep the game identity simple and direct. Do not lead with comparison language or AI-demo framing.

Naming Direction

The settled product name is Ricochet Rush.

Use this name in public UI, README copy, demo scripts, screenshots, and repository metadata. Keep the current local directory name for now.

Public repo: https://github.com/fitchmultz/ricochet-rush.

Done - Product Foundation

Status: complete through May 15, 2026.

The first production foundation is in place. Treat these as baseline capabilities to preserve, not as the next product bets.

Completed:

  • Original product identity, README, logo/icon assets, public docs, and clean repository positioning.
  • Three.js brick-breaker runtime with paddle rebound control, angled launches, anti-loop velocity correction, lives, score, combo multiplier, multiball, lasers, bombs, boss bricks, power-ups, particles, shake, and procedural audio.
  • Curated board packs with unlock progress, previews, best scores, and local Saved Designs for kept generated boards.
  • Prompt-first Board Designer powered by the Cursor SDK through the local Node route, with deterministic fallback generation when credentials are unavailable.
  • Compact Play Console, focused Designer/Boards/Options/Log panels, local save/restore, accessibility-oriented overlays, and responsive layout.
  • Automated verification through npm run ci, including build, unit tests, smoke, and desktop/mobile UX audit screenshots and reports.

Current product diagnosis:

  • The game functions well and the automated UX audit is green.
  • The next gap is not more mechanics. The gap is feel, personality, clarity, and the post-run loop.
  • Existing shake, particles, 3D lighting, combo, power-up art, and audio are useful starting points but are too subtle in screenshots and early play.

P1 - Screenshot Polish And 3D Read

Goal: make the first desktop and mobile screenshots read as a finished arcade game rather than a clean prototype.

Status: complete as of 2026-05-18.

Delivery notes: the playfield now uses per-brick rim/shadow accents, theme-aware grid/starfield atmosphere, paddle glow/specular feedback, and ball glow/trail treatment. Reduced-motion mode keeps the static read while removing background drift and heavy motion. Verified with npm run ci and manual review of the generated desktop/mobile UX audit screenshots.

Scope:

  • Strengthen brick depth with clearer bevel/rim edges, soft shadowing, and material differences for hard, bomb, boss, prize, and penalty bricks.
  • Make the background treatment visible: subtle parallax starfield or grid, pack theme color drift, and depth fog/back-wall atmosphere.
  • Add a faint specular sweep and stronger contact shape change to the paddle.
  • Add a readable speed trail or glow state to the ball without hiding its exact position.
  • Keep brick color semantics stable so power-up and hazard readings do not regress.

Acceptance criteria:

  • The default desktop screenshot reads as a distinctive arcade game, not a flat canvas.
  • The mobile screenshot still clearly shows ball, paddle, bricks, and current action.
  • Reduced-motion mode disables or tones down intense movement effects.
  • npm run ci and manual screenshot review stay green.

P2 - HUD And Player Language Cleanup

Goal: remove dashboard feel and make all always-visible text player-facing.

Status: complete as of 2026-05-18.

Delivery notes: the HUD now groups score/best, lives, and level/bricks into compact player cards, moves combo into an in-play streak badge, keeps technical generation/fallback details out of the default play rail, and uses a single compact mobile HUD bar. Mobile audit canvas size increased from 372x248 to 388x259 without overflow.

Scope:

  • Replace the six separate HUD pills with grouped information: Score / Best, Lives ●●●, Level · Bricks, and a combo readout near the playfield only when active.
  • Replace default Latest dev-log messages with short player-facing events and hints.
  • Move technical generation, atlas, trace, and loading diagnostics out of the default play rail and into the Log panel.
  • Compress the mobile HUD to a single compact bar so the canvas gains vertical room.
  • Keep the current accessibility live region and clear focus behavior.

Acceptance criteria:

  • No default visible text says things like Generated power-up atlas loaded.
  • The combo readout feels like a live streak reward rather than a static stat.
  • The mobile canvas is materially larger than the current audited 372x248 display without creating overflow.
  • The right rail reads as player help and recent action, not an engineering console.

P3 - Hit Juice And Game Feel Amplification

Goal: make ordinary hits feel rewarding every few seconds by amplifying existing systems before inventing new mechanics.

Status: complete as of 2026-05-18.

Delivery notes: brick hits now emit material-scaled chip/crumble bursts, bombs and bosses trigger impact rings plus brief flashes, paddle contact uses stronger visual squash/stretch, combo rewards use live streak badges and bigger pop text, and power-up catches emit ring bursts with supported haptics while respecting particles and reduced-motion settings.

Scope:

  • Increase brick chip/crumble particles by brick material and remaining HP.
  • Make bomb chains and boss hits heavier through stronger but brief screen shake, flash, and particle rings.
  • Make paddle contact squash/stretch more visible while preserving precise collision feel.
  • Escalate combo feedback with bigger pops, color flash, and score multiplier surge as the streak grows.
  • Add power-up catch bursts and optional touch haptics for meaningful brick breaks or catches when the browser supports vibration.

Acceptance criteria:

  • A brick break has obvious cause, impact, and reward without reading the HUD.
  • Boss, bomb, normal, and chipped hard-brick hits feel different.
  • Effects obey particles and reduced-motion settings.
  • No effect blocks ball/paddle readability during multiball.

P4 - Procedural Audio Identity Pass

Goal: make the existing procedural audio feel like an intentional arcade identity, not lightweight placeholder bleeps.

Status: complete as of 2026-05-18.

Delivery notes: paddle hits now layer low body with brighter attack, brick SFX pitch/intensity varies by material, damage, break state, and combo, combo streaks get throttled ascending tones, and explosions, boss damage, and volatile power-ups add controlled rumble/noise layers. The system remains fully procedural and smoke coverage checks independent volume controls plus a non-clipping SFX output guard.

Scope:

  • Add more harmonic body and low-end weight to paddle hits.
  • Vary brick hit and break pitch by brick type and combo state.
  • Add ascending streak tones for combo chains without creating spam in multiball.
  • Add controlled rumble/noise layers for explosions, boss damage, and volatile power-up chains.
  • Keep audio generated or clearly licensed; avoid large audio-asset dependencies unless they materially improve identity.

Acceptance criteria:

  • SFX and music volume controls remain independent and persistent.
  • Rapid brick chains stay readable and do not clip harshly.
  • Audio communicates paddle hit, brick class, danger, reward, and run state without needing the HUD.

P5 - Run Summary And Score Loop

Goal: close the loop after level clear or game over so a run ends with meaningful feedback and a clear next action.

Status: complete as of 2026-05-18.

Delivery notes: level clears and game-over states now use a full run summary overlay with score, best-score delta, bricks broken, longest streak, power-ups caught, boards cleared, and clear/survival time. The actions are keyboard-focusable and touch-sized, covering continue, retry, choose board, keep generated board when eligible, and a disabled share hook placeholder for the future export task. Run stats are saved with checkpoints so normal transition timing does not erase the summary.

Scope:

  • Add a level-clear summary and a game-over summary.
  • Track and show score, best score delta, bricks broken, longest combo or streak, power-ups caught, boards cleared, and clear/survival time.
  • Show direct actions: continue, retry, choose board, keep generated board when eligible, and later share/export when that system exists.
  • Keep the overlay keyboard and touch accessible.

Acceptance criteria:

  • Clearing a board and losing a run both produce a satisfying summary instead of only a short text modal.
  • Summary stats are derived from local run state and survive normal level transition timing.
  • The next action is clear on desktop and mobile.

Saved Designs stores source prompt and per-board best score, migrates older saved boards with defaults, and exposes each generated board as a replayable gallery card with thumbnail, saved date, prompt, and score metadata while preserving the shared board validation path.

Scope:

  • Show a generated-board preview thumbnail and summary before the player commits to play when practical.
  • Upgrade Saved Designs from a single pack entry into a browseable local gallery of individual generated boards.
  • Store and display each saved board's name, thumbnail/preview, saved date, source prompt, and best score.
  • Add keep, replay, remix, and discard language for generated boards.
  • Migrate existing saved-board data without losing boards.

Acceptance criteria:

  • A player can judge a generated board before or immediately after committing to it.
  • Saved Designs can be browsed per board, not just as one anonymous pack.
  • Existing saved generated boards continue to load through the shared validation path.

P8 - Shareable Board State And Score Card

Goal: make good generated boards and good runs portable without accounts or backend storage.

Status: planned.

Scope:

  • Add export/import for compact board JSON or deterministic seed data where stable enough.
  • Add a locally rendered PNG score card with score, board name, run stats, and a small board snapshot.
  • Keep exported data public-safe and versioned so old exports can be validated or rejected cleanly.
  • Do not add remote leaderboards, accounts, or cloud sync in this phase.

Acceptance criteria:

  • A strong generated board can travel to another browser profile.
  • A final score can be saved as an image from the browser.
  • Import validation rejects malformed or unsupported board data without breaking local saves.

P9 - Daily Challenge And Local Retention

Goal: create a cheap reason to return after shareable board state is stable.

Status: planned after P8.

Scope:

  • Add one deterministic daily board per local date.
  • Store local daily best score and completion state by date.
  • Surface Today's Board in the board picker with clear local-only language.
  • Allow daily score cards to reuse the P8 score-card path.

Acceptance criteria:

  • The same date produces the same daily board for a given app version and seed policy.
  • Daily progress persists locally without accounts.
  • The system does not depend on remote services after the app loads.

P10 - Cosmetics And Pack Progression Rewards

Goal: reward repeat play with visual progression that does not change balance.

Status: planned after the core loop and sharing work.

Scope:

  • Add unlockable paddle skins, ball trails, and optional board backplates tied to pack completion or medals.
  • Add a lightweight cosmetic picker under Options or the Saved Designs / Boards surface.
  • Keep all unlocks local and cosmetic-only.
  • Make cosmetics respect high contrast and reduced-motion settings.

Acceptance criteria:

  • Cosmetics never change paddle size, ball speed, score, or drop rates.
  • Pack completion has a visible reward beyond clear count.
  • Unlocked choices persist locally and can be reset with local progress.

P11 - Reliability Gates And Live SDK Probe

Goal: keep confidence high while the game becomes more polished and stateful.

Status: planned and ongoing.

Constraints:

  • The live SDK probe must use the current Cursor SDK path and stay server-side.
  • The deterministic fallback path remains the default for CI and unauthenticated local testing.
  • Agents should not own public demo recording. Demo capture and final public demo selection are human-owned.

Scope:

  • Add or maintain an optional npm run sdk:probe that runs only when CURSOR_API_KEY exists, requests one generated board, verifies trace visibility, validates the compact grid, and confirms the board is playable.
  • Extend automated playability checks for level clear, game over, summary display, pack unlock, Saved Designs replay, board import/export, and a longer stability pass without console errors.
  • Keep npm run ci deterministic and runnable locally.
  • Use manual screenshot review for visual judgment after polish passes; record public demo videos only when the project owner chooses to do so.

Acceptance criteria:

  • npm run ci remains green without CURSOR_API_KEY.
  • The optional live SDK probe gives fresh evidence that the live Cursor path works when credentials are present.
  • Automation covers the important end states before public sharing: level clear, game over, summaries, pack unlock, saved-board replay, share/export validation, and longer-run stability.

Begin Here

Begin future work with P1, P2, and P3 as one milestone: screenshot polish, HUD/player-language cleanup, and hit-juice amplification. These are the highest-leverage fixes because the current game already works, but its strongest systems are too subtle in the first screenshots and in early play. Keep the implementation path plain TypeScript, Vite, Three.js, and DOM HUD. Do not add remote accounts, leaderboards, player-facing model selectors, or new core mechanics until the feel, clarity, and run loop are stronger.
